## B-001 · 记账事件不一定落库

- 发现：2026-11-18，E2E 场景 e
- 现象：对 CFO 说"买了个镜头，300 块"，回复正常，但 `events` 里没有这条；秘书简报里也读不到。
- 反例：同一天另一次同样的输入，事件写进去了（`spend / 镜头 / 30000 / opex`）。
- 根因：未知。写回依赖模型在正文末尾输出 ```event {...}``` 块，模型可能省略、改写格式，或写成多块。
- 影响：未知。可能只影响记账，也可能影响 decision / package 三类写入（同一机制）。
- 不能现在改的原因：改了就无法判断是"提示词不可靠"还是"解析/校验有问题"，两件事的修法完全不同。
- 复现：
  ```bash
  curl -s -X POST localhost:8001/api/agents/cfo/messages \
    -H 'Content-Type: application/json' \
    -d '{"body":"记一笔：我买了个镜头，300 块，走运营。"}'
  curl -s localhost:8001/api/state | jq '.entries'
  ```
- 收敛方向（未采纳）：
  1. 换成工具调用（opencode API 支持 tools），把"手写 JSON"变成"结构化返回"。
  2. 保留块协议，但加一次自动重试：缺块时追问一句"这笔要不要入账"。
  3. 双写校验：解析失败也落一条 `event.reject` 审计（已做），用它统计失败率。
- 先要量出来的：连续 20 次同义输入，写入成功率是多少。有了这个数，再决定改法。

## B-005 · 单轮对话耗时异常（994s / 1158s / 1627s）

- 发现：2026-11-18，persona 版 E2E
- 现象：三轮对话跑了 16–27 分钟；同一时期普通对话是 6–8 秒。
- 根因：未知。怀疑三处：注入的「公司现状」让 prompt 变大；后台 6 秒 tick 与对话抢同一个模型服务；persona 与 CxO 同时调用造成排队。
- 影响：测试不可用（一次跑 40 分钟），线上体感也会崩。
- 先要量：单次 generate 的耗时分布（p50/p95），以及带/不带 facts 的对比。
